- 2026-10-26 · Phase 1 · Status emails (submitted / approved / needs info / rejected) are sent over SMTP with nodemailer instead of the Resend SDK. Gmail works now, and Resend at launch is only an env change (smtp.resend.com), so `RESEND_API_KEY` became `SMTP_*` + `EMAIL_FROM`. Sending runs in `after()` and never throws, so a mail failure cannot undo a submission or a review decision.
- 2026-10-26 · Phase 1 · Document retention: `expired_verification_documents()` (SQL, pgTAP-tested) decides what is due, and `/api/cron/purge-documents` deletes it through the Storage API daily via Vercel Cron, guarded by `CRON_SECRET`. This replaces a pure pg_cron job because Supabase blocks direct deletes from storage tables. The rule also removes files orphaned by resubmissions and uploads never submitted.
- 2026-10-29 · Phase 1 · Abuse protection is split by where requests go. Sign-up, email codes and password login go browser → Supabase Auth, so Turnstile is enforced by Supabase's built-in captcha (the app sends `captchaToken`). Our server actions get Upstash sliding-window limits: proof upload/submit 10/h per user, waitlist 5/h per IP plus a server-side Turnstile check. Rate limits fail open on an Upstash outage; Turnstile verification fails closed. Both are no-ops until their keys are set.
- 2026-10-29 · Phase 2 · Other students read profiles only through the `profiles_public` view (safe fields, rows filtered by `profile_visibility`, photo/hometown masked); the base `profiles` table is now self + admin. `visible_at`/`can_view_profile` use `auth.uid()` instead of taking a viewer argument (§4.4 shows one), because a viewer argument would let anyone probe whether two other students share a department or batch. `connections` visibility means "only me" until Phase 4 replaces `are_connected()`.
- 2026-10-29 · Phase 2 · Avatars are cropped and resized in the browser into 512 px and 128 px WebP (`avatars/{user}/{version}-{size}.webp`), because Supabase image transformations need a paid plan.
- 2026-10-29 · Phase 2 · Linking a UoS email later uses our own 6-digit code instead of Supabase's change-email flow, because changing the auth email would also change how the fresher logs in. The code is made with `crypto.randomInt`, emailed over SMTP, and stored only as sha256(`user:code`) in `uni_email_claims` (service-role only). It expires after 10 minutes and allows 5 tries, with 5 codes/h and 20 checks/h per student. The UOS EMAIL stamp now means "a UoS email is on file" (`private_profile.uni_email`), not "signed up by email"; `verification_method` keeps how the student was verified.
- 2026-10-29 · Phase 2 · Editing the profile reuses setup screens 6–8 with `?edit=1` (no step dots, "Save", back to `/me`), honoured only after setup is finished. Privacy has its own `/me/privacy`. `/people/[handle]` treats hidden and missing profiles the same (404), so handles can't be probed, and leaves names out of the tab title. The completeness meter counts 7 things (photo, bio, hometown, section, 3+ interests, Opening Move, UoS email).
- 2026-10-30 · Phase 3 · The `blocks` table arrives now instead of Phase 4, because discovery must already hide blocked students; a block hides each student from the other in `visible_at`, the directory and suggestions. The directory, its counts and `suggest_people` are security-definer SQL functions that apply the `visible_at` rule for a whole page at once (the per-row check is too slow for 30k profiles); pgTAP compares them with `profiles_public` at every visibility level. Pages are keyset on (lowercased name, id). Students who leave the directory are findable only by their exact handle. Counts include only students the viewer could find. Suggestions use the §4.7 weights without shared courses and mutual connections until those exist; the 40% top-reason cap is applied in the app (`lib/discovery.ts`).
- 2026-10-30 · Phase 3 · The directory list relies on CSS `content-visibility: auto` on each card plus 30-row keyset pages ("Load more") instead of a JS virtualiser, which adds no bundle weight and keeps rows accessible to find-in-page and screen readers. The feature dock and batch reveal use `motion` through `LazyMotion` + `domAnimation` (springs per §6.3, off under reduced motion); `/explore` first load is 168 KB, inside the 200 KB budget. The bottom nav shows Feed, Backup and Chats as "Soon" until those phases land, instead of linking to empty pages. Suggestions are cached per student in Upstash for 15 minutes (`lib/redis.server.ts`, read-through, falls back to computing on any Redis error).
- 2026-10-30 · Phase 3 · Invites: one 8-character code per student (`my_invite_code()`), a public `invite_preview()` that shows only the inviter's first name, their department batch and a count, and an `/i/{code}` page with a `next/og` share image. "Join your batch" goes through `/i/{code}/join`, which stores the code in an httpOnly cookie for 30 days; it is redeemed when the new student finishes setup (once per student, never your own code), so `uses` counts people who actually joined. The 30k-student speed check seeds with SQL `generate_series` instead of a faker script (no dependency, seconds instead of minutes, rolled back) and runs in the CI db job, failing above 300 ms p95 across directory queries; counts and suggestions are reported but not gated.
- 2026-10-31 · Phase 4 · Connections and chat write only through security-definer functions (request/respond/remove connection, start_dm, send_message, mark_read, block, report, join_batch_chat, create_group…), so each write checks verification, blocks, profile visibility and `allow_dms_from` in one place; RLS grants only reads (members-only messages). The `connections` table has no read policy at all: students see it through `connection_state()`, `incoming_requests()` and `my_connections()`, so a sender is never told they were declined (it stays "outgoing"; re-asking within 30 days does nothing). `are_connected` is no longer callable by students. DMs from non-connections land in Requests (`accepted_at` null) until answered; declining deletes the chat. Blocking ends the connection and hides the DM from both lists. Typing indicators use private Realtime broadcast channels `conversation:{id}` guarded by an RLS policy on `realtime.messages`. Photos go to a private `chat-attachments` bucket under `{conversation_id}/`, readable by members only.
- 2026-10-31 · Phase 4 · Message and connection-request rate limits are enforced in the database (triggers on `messages` and `connections`: 60 messages a minute, 30 requests a day, errcode 54000), not only in server actions, because `send_message` and `request_connection` are callable directly with a student's own token. With that in place the chat sends straight from the browser to `send_message`, skipping a hop through Next.js. Delivery is measured in the browsers (Enter on A to the text appearing on B, same machine clock). Group chats: batch and section chats are offered under Groups and joined explicitly; custom groups are built from your connections. Blocked students are listed under Me → Blocked.
- 2026-11-02 · Phase 5 · No FastAPI/pgmq worker is hosted yet, so Phase 5's jobs run without one: the Backup fan-out runs in SQL inside `create_backup` (tiers: same section, department batch, department mentors; 50 cap; skips muted, blocked and anyone with 5 Backup pings today), expiry is a `pg_cron` job every 10 minutes, and push delivery (part 3) is triggered from the database. The plan's worker can take these over later. Students never read `posts`/`comments`: `posts_public`/`comments_public` return `author_id = null` and a per-thread alias ("Kinnow #42") for anonymous content; post photos live in a private bucket under random names so a path can't identify an anonymous author. Anonymous posting is behind the `anonymous_posts` feature flag (off), with 3 posts/day and a hold after 2 reports (named: 10/day, hold after 5). Notifications are written only by `notify()` (skips self, muted types and blocks); anonymous actors are stored as null. Views call a caller-only `blocked_with(other)` because a view's functions run with the reader's permissions. The Supabase CLI mis-split one plpgsql body containing `case … end then`; such checks are written as plain `if` blocks.
- 2026-11-02 · Phase 5 · Web Push without a worker: an AFTER INSERT trigger on `notifications` (and on `messages`, for chats) calls `pg_net` to POST `{kind, id}` to the app's `/api/push` with `Authorization: Bearer PUSH_WEBHOOK_SECRET`; the route loads the row with the service role, applies push/message preferences, mutes and blocks, and sends with `web-push` (VAPID), deleting subscriptions the push service reports gone (404/410). The URL and secret live in `app_private.config`, a schema the API can't reach; until they are set the database sends nothing (local development can't be reached from the hosted database anyway). The browser is asked for permission only after a meaningful action (on the notification centre once something has arrived, or after asking for Backup), never on page load. `getSession` is wrapped in React `cache` so a page and its shell (the bell) share one auth lookup.
- 2026-11-03 · Phase 6 · Courses are added by students (no official catalogue was available): `add_course` normalises codes (`cs 301` = `CS-301`) per department, so the first student creates a course and everyone after picks it; 10 new courses/day per student. Course pages are addressed by id because codes repeat across departments. Terms follow UoS (Fall Sep–Jan, Spring Feb–Jun, Summer Jul–Aug, Pakistan time). Without a hosted worker there is no virus scan yet: resources accept only PDF/JPEG/PNG/WebP up to 10 MB, publish immediately, and are held after 3 reports (`pending_scan` stays reserved for a scanner). Timetables are private; "Free together" reads only busy times (no course, room or label) of connections who leave `share_free_time` on. "Who's free now" uses an opt-in `show_free_now` plus an "I'm on campus" toggle that expires (≤ 8 h) instead of Redis presence. Pings are a new `ping` conversation kind lasting 2 hours (10/day, respecting `allow_dms_from`). Mentoring opens from semester 3 (students set `is_mentor` through `set_mentor`); an accepted mentorship also connects the pair so they can message. The Backup fan-out gains its first tier: classmates enrolled in the request's course. Timetable screenshot import waits for the AI service (Phase 7); the GPA calculator waits for the UoS grading table.
- 2026-11-03 · Phase 6 · The GPA calculator uses the official UoS grading table supplied by the project owner (80–100 = A 4.00; 65–79 = B, 3.94→3.00; 50–64 = C, 2.92→2.00; 40–49 = D, 1.90→1.00; below 40 = F 0), on whole marks, weighted by credit hours; CGPA weights every course across semesters (not an average of GPAs). Per the table's note, courses under 50% are flagged as below the semester-system pass mark while still showing their table grade points. Results like RL, W, R and I carry no marks and are left out. Grades are saved only in the browser (localStorage), never on the server.
- 2026-11-03 · Phase 7 · AI choices (project owner): Anthropic Claude, **`claude-haiku-5-5` for every AI feature** (cheapest current model; about $0.001 per AI Buddy answer at ~6K tokens in / 600 out), run inside the Next.js app on Vercel instead of the planned FastAPI service (no extra hosting). Embeddings use Supabase's built-in **gte-small** (English, 384 dimensions, free) in an Edge Function; the plan's 1024 dimensions follow the chosen model. gte-small reads at most 512 tokens, so excerpts are ~350 words with 50 overlap (not 800 tokens) and never cross pages, so citations can name a page. Search is hybrid (20 by meaning + 20 by keywords, reciprocal rank fusion, top 6) inside `search_course_chunks`, which only reads published files of the requested course at the caller's university; excerpts aren't otherwise readable. The `embed` function keeps the gateway's JWT check on and is called with the signed-in student's own token (the project's service key is a non-JWT secret key, and turning verify_jwt off was declined); it also rejects non-`authenticated` roles. Text PDFs are read with `unpdf` (no AI cost); photos and scanned PDFs are transcribed by Claude, with the file treated as data to copy, not instructions. Daily AI quotas (30 Buddy questions, 10 timetable imports, Pakistan days) are enforced in the database. Moderation decisions are HMAC-signed by the server and verified in `create_post`/`create_comment` against `app_private.config.moderation_secret`, so calling the functions directly can't skip moderation; with no secret set (development, CI), moderation is off. In CI, `AI_FAKE=1` swaps in deterministic stand-ins for Claude and embeddings (no key, no cost).
- 2026-11-03 · Phase 7 · Moderation, verification pre-check and timetable import. Moderation labels each post and comment with Claude (allow / hold / block, stricter for anonymous posts, the text wrapped as data); "block" is refused with a message, "hold" saves the post as held (the author sees "Under review"). If the label can't be fetched the post is held rather than published unchecked. Photos aren't checked by AI yet (reports still hold them). Before `moderation_secret` is set in the database, an unsigned "held" is still honoured, since holding only hides the author's own post. The verification pre-check runs after submission (`after()`), has Claude read the document into fields, and scores them in code (name token match, roll number match, UoS keywords, possible edits, a roll number used by another account); `ai_precheck` only sorts the admin queue (highest confidence first) and shows flags. Nothing is auto-approved. Timetable import goes through a route handler (server actions cap bodies at 1 MB; images up to 4 MB), returns classes without saving, and saves only what the student confirms; times like "1:30" without AM/PM read as afternoon, and known course codes link to the student's courses.
- 2026-11-04 · Phase 8 · Campus life, core only (the roommate finder and campus places, both P2, wait). The plan's `women_only_spaces` toggle can't prove eligibility and the app records no gender, so (project owner's choice) students ask for women-only access on Privacy and an admin confirms it (`women_only_access`, `/admin/campus`); women-only rides are hidden by RLS and `can_see_ride` from everyone else, including from the ride board and seat requests. Rides use `kind` offer/request instead of the plan's driver/passenger enum, `recurring_days` (0 = Monday) instead of JSON, and areas as free text with a drafted list of campus gates, Sargodha areas and nearby cities for the owner to correct. Accepting a seat creates (or joins) the ride's group chat, so phone numbers are never needed; offers fill at their seat count, requests after one lift. Listings use the same signed AI moderation as posts (over "title\ndescription"), a private `listing-media` bucket, and are held after 3 reports; "Message" opens a DM with a prefilled (unsent) line. Societies are created by students and listed only after an admin verifies them; their admins post events, and app admins can post campus-wide ones. RSVPs are going/interested with capacity on "going"; a pg_cron job every 5 minutes notifies RSVPs about events starting within the hour (push follows through the existing notification trigger), and each event downloads as an .ics file with a 1-hour alarm. The explore dock now has 8 live tiles in a 4-column grid (Events and Timetable added).
- 2026-11-05 · Phase 9 · Trust and admin. Every admin and moderator action goes through a security-definer function that calls `audit()` (actor, action, before/after); pgTAP checks each one writes `audit_log`. Student moderators get `role = moderator` plus `moderator_scopes` (campus feed or a department feed) and can remove/restore posts and comments and dismiss reports only there; admins act on everything, and only admins ban. The plan's PostHog flags became the existing `feature_flags` table (with an audited admin page) because flags like anonymous posting must be enforced in SQL; PostHog stays for analytics. DAU/WAU come from `activity_days`, recorded once a day per browser by the middleware (a cookie avoids a write per request); daily stats are a materialised view refreshed hourly, and retention is shown as weekly cohorts by verification date. Account deletion deactivates at once (`deleted_at` already hides a profile everywhere) and a daily pg_cron job deletes the `auth.users` row after 14 days, cascading to the profile and private details; messages they sent stay in others' chats without a name, and the daily retention route removes their leftover Storage files (SQL can't). Exports are built in SQL as the student, stored privately for 7 days and emailed as a signed link (once a day). Guidelines are accepted once before a first post, comment or listing (checked in the server actions; test students are pre-accepted). Badges are awarded hourly by an idempotent job; the Backup Hero board counts this month's resolved requests (Pakistan time). The weekly digest goes out Sundays 7 pm PKT, only to students with something new, capped at 400 a run for Gmail's limit, with a signed unsubscribe link that asks for confirmation so link scanners can't unsubscribe anyone. Banned accounts see only `/banned`; accounts awaiting deletion only `/me/data`. Safety centre emergency numbers (15, 1122, 1043, 115) should be confirmed by the project owner before launch.
- 2026-11-06 · Phase 10 · Launch polish. The service worker serves pages from the network only (they're personal and live) with an offline page as the fallback, and caches hashed build assets and icons; the "Add to Home Screen" prompt uses the browser's install event on Android and two-step instructions on iPhone Safari, quiet for 30 days after "Not now". Lighthouse CI (mobile, public pages) and axe (WCAG 2.1 AA, both themes, public and signed-in pages) now gate CI; first-load JavaScript is 103–175 KB per page, within the 200 KB budget. The first k6 run (100 students on one CI runner) found the feed at 4.4 s p95: `posts_public` is a security_barrier view, so ordering and limiting from outside couldn't use the index. Rather than drop the barrier, `feed_page()` walks the index and looks each post up in the view (laterally, by id), so only one page is built; the messages policy reads the caller's chats once per query, and `last_message_at` is refreshed at most once a second. A CI runner can't hold 500 concurrent students (its local connection pool runs out), so the 500-user run is meant for staging; `docs/SECURITY.md` and `docs/RUNBOOK.md` record the review and operations, and `docs/DEPLOY.md` the production steps. CSP keeps `'unsafe-inline'` scripts (a nonce would make every page dynamic, including the offline page); risk is low and recorded. Browser targets are now Chrome/Edge/Firefox 109+, Safari 15.4+ and Samsung Internet 21+.
